## Goal
One plain format for API smoke scenarios, one folder per feature, so writer (SM02) and runner (SM03) share one contract.
## DoD
- `smoke/<feature>/scenarios.yml` schema documented in `smoke/README.md`
- fields: id, env (tst|acc), method, path, auth (none|smoke-jwt), expect.status, expect.json (jsonpath equals/exists), test_data_only: true for any write
- check-smoke.sh validates schema, rejects prd, rejects write without test_data_only
- good + 3 bad fixtures, wired into verify.sh and POL23
## Steps
1. write README + schema
2. write check-smoke.sh (yq)
3. fixtures: good, prd env, write without test_data_only, missing expect
4. wire into verify.sh
## Technical design
- Components and files: smoke/README.md, smoke/_schema.yml, scripts/check-smoke.sh, tests/fixtures/smoke/{good,bad-*}.yml, scripts/verify.sh
- Module boundary: `smoke/<feature>/scenarios.yml` plus `scripts/check-smoke.sh` (exit 0/1); the schema rules (env, auth, expect, test_data_only) sit behind it
- Interfaces: input scenarios.yml; exit 0 ok, 1 failed (PA5)
- Sequence:
  ```mermaid
  flowchart LR
    A[PBI acceptance criteria] --> B[smoke/feature/scenarios.yml]
    B --> C[check-smoke.sh]
    C -->|0| D[verify green]
    C -->|1| E[verify red, rule named]
  ```
- Failure modes: bad scenario fails verify with the field named
- Security: no URLs with secrets, no tokens in files; base URL comes from environment vars, not files
- Observability: verify log line per file
- Cost: 0
- Rollback: revert the PR
